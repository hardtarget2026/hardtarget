# HardTarget Security Posture

HardTarget is a security tool that runs with admin and SYSTEM privileges. It applies fixes to Windows configuration. A tool with that level of access has to protect itself at least as aggressively as it protects the machines it runs on. This document explains how.

## Script Integrity: The Elevation Path

HardTarget needs admin rights to apply most fixes. When you run it as a standard user, it asks Windows to relaunch itself as admin through the UAC prompt. There is a gap between "you clicked yes on the UAC prompt" and "the admin copy starts running." An attacker who can write files on your machine could try to swap in a malicious script during that gap, and Windows would run it as admin.

HardTarget closes this gap with a six-step chain:

1. **Lock and read into memory.** The script atomically resolves its own path through all directory redirections (junctions, symlinks) using the Windows kernel, locks the file via the same kernel handle, reads the entire file into memory, and releases the lock. The lock window is microseconds. Once the content is in memory, the disk file is irrelevant.

2. **Hash the in-memory content.** The script computes a SHA256 hash of the in-memory bytes.

3. **Create a secure named pipe.** The script creates a named pipe server with a cryptographically random name, restricted to Administrators-only access, limited to a single connection.

4. **Build an immutable bootstrapper.** The script generates a tiny PowerShell bootstrapper (about 15 lines) containing the pipe name and the expected hash as hardcoded string literals. This bootstrapper is Base64-encoded.

5. **Launch elevated via encoded command.** The script calls `Start-Process -Verb RunAs` with `-EncodedCommand` carrying the bootstrapper. The moment `Start-Process` is called, the bootstrapper is locked into the Windows `AppInfo` RPC call. It is immutable from this point forward, regardless of what happens to the non-elevated process.

6. **Pipe the content to the elevated process.** After UAC approval, the elevated process runs the bootstrapper. The bootstrapper connects to the named pipe and receives the script content directly into memory.

7. **Verify and execute from memory.** The bootstrapper hashes the received content, compares it to the hardcoded expected hash, and if they match, executes the script from memory via `[scriptblock]::Create()`. The elevated process never reads from the disk file.

8. **If any step fails, stop.** If native APIs are unavailable, the pipe connection fails, or the hash does not match, the script aborts.

## Dashboard Security: Browser to Console

HardTarget has a web dashboard for reviewing scan findings and applying fixes. The dashboard runs in your browser. The fix engine runs in a PowerShell console. Every fix request from the browser must pass through four layers of validation before anything changes on your system.

### Layer 1: Console Confirmation Codes

When you click "Apply Fix" in the dashboard, the browser sends a request to the local HTTP server. The server accepts the request but holds it. A random 6-digit confirmation code (generated by the operating system's cryptographic random number generator) appears in the PowerShell console window. You have to physically type that code into the console to approve the change. A malicious website, browser extension, or background process has no way to type into your console window. Only someone sitting at the keyboard can approve a fix.

### Layer 2: Authentication Token

Every request from the dashboard carries a 32-character cryptographic token in a custom HTTP header (`X-HT-Auth`). The token is generated fresh each session using CSPRNG and delivered only through an ACL-protected file on disk. It is never embedded in URLs, query strings, or browser history. Token comparison uses constant-time XOR accumulation to prevent timing side-channels.

### Layer 3: Origin and Cross-Site Protection

The server validates the `Origin` and `Sec-Fetch-Site` headers on every mutating request. Cross-origin requests from other browser tabs or websites are rejected. All mutating endpoints require POST (preventing accidental triggering through prefetch, image tags, or redirects).

### Layer 4: Localhost-Only Binding

The server binds to `127.0.0.1`, so only processes on the local machine can reach it. The traffic stays on your computer.

### Idle Timeout

The fix engine locks automatically after 15 minutes of inactivity. Fix requests received after the idle timeout are rejected server-side, regardless of whether the dashboard session appears active in the browser.

### Read-Only Mode

Audit mode disables all fix and mutation endpoints at the server level. The dashboard becomes a read-only scan viewer with no ability to trigger changes, even with a valid token and console access.

## Fix Engine: What Can Change and How

HardTarget applies fixes through a closed set of operations. There is no general-purpose command execution.

### Fix Types

Every fix is a static definition in the `$script:FixDefs` registry. Each definition declares its type and its exact parameters. The fix engine supports these types only:

- **registry**: Sets a specific registry value at a specific path. The path, key name, value, and type are all declared in the fix definition.
- **multi-registry**: Sets multiple registry values in a single operation.
- **command**: Executes a system binary. Only five executables are permitted: `powercfg.exe`, `reagentc.exe`, `bcdedit.exe`, `net.exe`, and `vssadmin.exe`. Each is referenced by its fully qualified `System32` path (resolved once at startup from `%SystemRoot%\System32`). Any command referencing a binary outside this list is blocked and throws an exception.
- **service**: Changes the startup type of a specific Windows service.
- **script**: Runs a hardcoded inline operation for complex fixes (such as enumerating all user registry hives for per-user cleanup). These are switch-case matched by fix ID, so only the exact operations coded into the script can execute.

There is no eval, no Invoke-Expression, no arbitrary string execution, and no way for the dashboard to inject a command that the fix engine will run.

### Fully Qualified Binary Paths

All external executables are resolved to their full `System32` path at startup (`C:\Windows\System32\powercfg.exe`, etc.). This prevents PATH hijacking, where an attacker places a malicious `powercfg.exe` earlier in the PATH environment variable. After UAC elevation, the user-level PATH is merged into the elevated process, so unqualified binary names are exploitable. HardTarget never calls an unqualified binary name.

### Post-Fix Verification

After applying a fix, the engine re-runs the original scan check for that finding. The dashboard reports whether the fix actually took effect, rather than assuming success.

### Restore Points

Before applying fixes, the dashboard offers to create a Windows System Restore point. This is gated by the same console confirmation code system.

## File Operations: Atomic Link-Safe Deletion

When HardTarget deletes files in directories where standard users have write access (such as forensic artifact cleanup), it uses native Win32 APIs through an in-memory pre-compiled assembly (`HtNativeFile`):

1. `CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT` opens the link itself, never following it to a target.
2. `GetFileInformationByHandle` checks for hardlinks and reparse points on the actual opened file object.
3. `SetFileInformationByHandle` marks the file for deletion through the same handle.

The handle is held continuously from open through check through delete. There is zero gap for an attacker to swap a symlink or hardlink between the safety check and the deletion.

## Data Storage: ACL-Protected Directories

All data written to disk (scan results, auth tokens, baseline files) goes into `C:\ProgramData\HardTarget`. This directory is created using a staging pattern:

1. Create a directory with a cryptographically random name.
2. Apply restrictive ACLs (SYSTEM and Administrators only) while the name is unpredictable.
3. Atomically rename to the final name.

This prevents an attacker from pre-creating the directory with permissive ACLs or substituting a junction. If the directory already exists, ownership and ACLs are verified and re-applied on every launch. If ACL enforcement fails while running elevated, the script aborts.

## Monitor Integrity

When installed as a scheduled task, the monitor verifies the script's SHA256 hash against the `InstalledHash` registry value before each run. A hash mismatch logs a critical event (EventId 9999) and aborts. This detects tampering with the installed copy between scheduled runs.

## Environmental Guards

- **32-bit process detection.** If the script detects it is running as 32-bit PowerShell on a 64-bit OS (which silently redirects all registry reads to WOW6432Node), it aborts immediately. Every scan result would be wrong and every fix would write to the wrong location.
- **Constrained Language Mode.** If CLM is active (via `__PSLockdownPolicy` or WDAC policy), the native security primitives are unavailable. The script aborts when elevated rather than degrading to weaker alternatives.
- **WDAC / AppLocker.** In environments with User Mode Code Integrity enforced, loading unsigned in-memory assemblies is blocked. The script will abort in elevated contexts on these endpoints. This is a known limitation: the in-memory loading approach that eliminates disk-based TOCTOU attacks is incompatible with UMCI enforcement. These environments typically have their own application control policies that provide equivalent protection.

## Known Limitations

These are fundamental to the single-file PowerShell architecture and cannot be fixed without a compiled, signed launcher binary.

### Same-SID Process Memory Injection

A standard user holds `PROCESS_ALL_ACCESS` to any process under the same SID. An attacker can use `WriteProcessMemory` to overwrite the in-memory script buffer in the non-elevated HardTarget process between the file read and hash computation. The bootstrapper will compute the hash of the attacker's payload, pass it through the pipe, and the elevated process will verify and execute it as Administrator.

**Why it is unfixable:** The non-elevated process must be writable by its owner — that is a Windows security boundary, not a bug. Only a compiled launcher with Protected Process Light (PPL) or code-signing enforcement can prevent same-SID memory writes. Both require leaving the single-file PowerShell architecture.

### AMSI / ETW COM Hijacking via HKCU

When PowerShell starts, it initializes AMSI (Anti-Malware Scan Interface) and ETW (Event Tracing for Windows) via COM `CoCreateInstance`. COM resolution checks `HKCU\Software\Classes\CLSID` before `HKLM`. An attacker can register a malicious native DLL under their own `HKCU` hive that shadows a known AMSI provider CLSID. When the elevated PowerShell process starts after UAC approval, COM loads the attacker's DLL as Administrator — before any PowerShell code executes, including the bootstrapper's environment scrubs.

**Why it is unfixable:** COM resolution happens inside the CLR and Windows loader during process initialization. Unlike environment variables (which can be scrubbed via a `cmd.exe` wrapper), registry-based COM resolution cannot be intercepted or redirected from a script. The only mitigation is a compiled launcher that creates the elevated process with a filtered token or restricted HKCU view, which violates the single-file architecture.

**Practical risk:** The attacker must know the exact CLSID of an AMSI provider loaded by the target PowerShell version, write a native DLL that survives `DllMain` initialization constraints, and pre-stage both the registry key and the DLL. This requires deep Windows internals knowledge and prior code execution on the machine.
