## v0.83 | Environment Scrub Fix + Pipe Hardening + Trust Boundaries

**`cmd.exe` environment scrub set variables to whitespace instead of clearing (HIGH — self-inflicted DoS):** The `set VAR= &` chain had trailing spaces before each `&` operator. In `cmd.exe`, any character before `&` is included in the assigned value. All scrubbed variables were set to `" "` instead of empty. On PS7 (.NET Core), `DOTNET_STARTUP_HOOKS=" "` caused the CLR to parse a space as an assembly path, terminating the process before any PowerShell code executed. **Fix:** Removed all spaces between `=` and `&`: `set VAR=&set VAR2=&...`.

**`__PSLockdownPolicy` missing from environment scrub (MEDIUM — DoS):** A standard user can set `__PSLockdownPolicy=4` in `HKCU\Environment`. `AppInfo` merges this into the elevated environment, forcing the elevated PowerShell into Constrained Language Mode. CLM blocks the bootstrapper's `NamedPipeClientStream` instantiation, crashing the elevation sequence. **Fix:** Added `set __PSLockdownPolicy=` to the `cmd.exe` scrub chain.

**Named pipe ACL over-permission — same-SID pipe theft (MEDIUM — DoS/data leak):** The creator SID was granted `FullControl`, which includes `ReadData` (client connection rights). Any malware running under the same SID could connect to the single-instance pipe, consuming it before the elevated bootstrapper. The attacker receives the full script content; the bootstrapper times out. **Fix:** Creator SID now receives `FullControl` minus `ReadData`, granting server-side management rights without client connection capability.

**PS7 pipe ACL fallback left pipe unrestricted (MEDIUM — DoS):** On .NET Core (PS 7+), the `PipeSecurity` constructor is unavailable. The fallback created the pipe with default permissions, then applied the ACL via `SetAccessControl`. If `SetAccessControl` failed, the `catch {}` block silently continued with an unrestricted pipe. **Fix:** ACL application failure now disposes the pipe and throws `SECURITY ABORT`. The TOCTOU window between creation and ACL application on PS7 remains (unavoidable without `NamedPipeServerStreamAcl.Create` in PS 7.4+) but is microseconds with a random pipe name.

**`$env:windir` and `$env:SystemDrive` trust boundary (MEDIUM):** Fix handlers used `$env:windir` for Amcache/SRUM paths and `$env:SystemDrive` for BitLocker, hibernation, and user profile operations. These inherit from `HKCU\Environment` via `AppInfo` registry merge. An attacker could redirect file operations to attacker-controlled paths. **Fix:** All `$env:windir` replaced with `$script:TrustedSystemRoot` (from `GetFolderPath`). New `$script:TrustedSystemDrive` derived from `$script:TrustedSystemRoot.Substring(0,2)` replaces all `$env:SystemDrive` usage.

**Staging directory `Move-Item` fallback created nested directory (HIGH — LPE to SYSTEM):** If `SafeRenameDirectory` failed because an attacker pre-created the target directory, the `Move-Item` fallback moved the secure staging directory *into* the attacker's directory instead of replacing it. The attacker's permissive ACLs remained on the parent. **Fix:** `Move-Item` fallback removed entirely. If atomic rename fails, the script aborts with `SECURITY ABORT`.

**Parameters dropped across UAC boundary (LOW — functional bug):** `-OutputDir` and `-Port` were silently lost during self-elevation. The bootstrapper only forwarded the mode parameter and hash. **Fix:** Extra parameters (`-OutputDir`, `-Port`, `-DryRun`, `-NoNVD`) are now serialized into the bootstrapper invocation line via `~~EXTRAS~~` placeholder.

**Browser auto-launch restored via `explorer.exe` de-elevation broker (UX):** v0.81 removed browser auto-open because `ShellExecute` from an elevated process reads HKCU protocol handlers. The dashboard URL now launches through `explorer.exe`, which always runs at medium integrity. The browser inherits the non-elevated token. Falls back to printing the URL on failure.

**AMSI/ETW COM hijacking via HKCU documented as unfixable (SECURITY.md):** COM `CoCreateInstance` during PowerShell initialization reads `HKCU\Software\Classes\CLSID` before `HKLM`. An attacker can shadow an AMSI provider CLSID with a malicious native DLL that loads as Administrator before any script code executes. This cannot be intercepted from PowerShell or `cmd.exe`. Documented alongside same-SID memory injection as a fundamental limitation of the single-file architecture.

## v0.82 | Pipe ACL + Startup Hooks + Parameter Elevation (112 cumulative findings)

**Named pipe ACL denied creator SID — local DoS (MEDIUM):** The `PipeSecurity` only granted `Administrators` `FullControl`, but the non-elevated process that creates the pipe does not have the `Administrators` group in its active token. The pipe creation threw `UnauthorizedAccessException`, and the `catch` block silently fell back to creating the pipe with a default unrestricted Security Descriptor. Any same-user process could connect to the pipe before the elevated bootstrapper (causing a `TimeoutException` DoS) or potentially inject content. **Fix:** The pipe ACL now grants `FullControl` to both `BUILTIN\Administrators` (for the elevated bootstrapper) and the creator's own SID (for the non-elevated server). The PS7 fallback applies the ACL post-creation via `SetAccessControl` instead of leaving the pipe unrestricted.

**`DOTNET_STARTUP_HOOKS` and `DOTNET_ADDITIONAL_DEPS` missing from environment scrub (MEDIUM):** The `cmd.exe` wrapper scrubbed CLR profiler variables but missed `DOTNET_STARTUP_HOOKS` (loads arbitrary assemblies before the entry point on .NET Core/5+) and `DOTNET_ADDITIONAL_DEPS` (injects dependency configuration). An attacker who sets these in `HKCU\Environment` could load malicious assemblies into the elevated `pwsh.exe` process. **Fix:** Both variables added to the `cmd.exe` `set VAR=` scrub chain.

**`-Install` and `-Uninstall` parameters skipped self-elevation (MEDIUM):** The `$needsMenu` guard evaluated to `$false` when `-Install` or `-Uninstall` was specified, skipping the entire elevation block. When run from a non-elevated prompt, these operations failed silently with `UnauthorizedAccessException` errors. **Fix:** A dedicated elevation block fires before the menu check when `-Install` or `-Uninstall` is specified and the process is not already elevated. Uses the same in-memory bootstrapper, pipe, and `cmd.exe` wrapper mechanism as the interactive menu path.

**UTF-8 BOM inconsistency in verify wrapper (LOW):** The bootstrapper stripped the UTF-8 BOM (`\uFEFF`) before `[scriptblock]::Create()`, but the auto-generated `HardTarget_Verify.ps1` wrapper did not. If the script was saved with a BOM by a user's editor, the monitor could fail on stricter runtimes. **Fix:** BOM stripping ported to the verify wrapper.

**Not fixed (assessed and triaged):** Forensic scan checks evaluating `HKCU`/`$env:APPDATA` instead of enumerating all user profiles. This is a functional accuracy issue (false PASSes on forensic checks for non-active profiles), not an LPE. Scheduled for a future release. Shell API folder spoofing via `HKCU\Explorer\User Shell Folders` assessed and dismissed: `SpecialFolder.Windows` and `CommonApplicationData` resolve from CSIDL_WINDOWS and CSIDL_COMMON_APPDATA, which are system-level and not influenced by HKCU User Shell Folders. `Initialize-SecureDirectory` managed fallback TOCTOU assessed: already covered by fail-closed logic on security-critical paths; the managed fallback only fires when native APIs are unavailable, and in that context the script already aborts on elevation paths. Verify wrapper paradox assessed: both files share the same ACL-protected directory, but the wrapper adds defense-in-depth against monitor-script-only overwrites and provides an external integrity verification point for the scheduled task entry.

## v0.81 | AppInfo Environment Rebuild + ProgramData + Browser Launch (108 cumulative findings)

**CLR profiler bypass via HKCU registry — LPE to admin (CRITICAL):** The v0.79 fix stripped `COR_ENABLE_PROFILING` from the parent process's environment, but `Start-Process -Verb RunAs` delegates to the `AppInfo` service, which does not inherit the parent's environment. Instead, `AppInfo` calls `CreateEnvironmentBlock` to build a fresh environment from `HKLM\...\Environment` merged with `HKCU\Environment`. An attacker who sets `COR_ENABLE_PROFILING=1` and `COR_PROFILER_PATH` in their `HKCU\Environment` registry key poisons every elevated managed process regardless of what the parent stripped. The .NET CLR loads the attacker's DLL before the first line of the bootstrapper runs. **Fix:** The elevation now routes through `cmd.exe` (native, CLR never loads) with `/c` that explicitly clears all CLR profiler variables via `set VAR=`, then launches `powershell.exe`. The child PowerShell inherits `cmd.exe`'s scrubbed environment, not the registry-merged one.

**`$env:ProgramData` poisoning — LPE to SYSTEM (CRITICAL):** Same vector class as `SystemRoot`: a standard user can set `ProgramData` in their process environment to redirect the monitor data directory, scheduled task scripts, and auth token storage to an attacker-controlled location. The attacker owns the parent directory and can rename it away after `Initialize-SecureDirectory` locks down the subdirectory, then recreate the path with malicious content. The scheduled task executes the attacker's script as SYSTEM. **Fix:** Introduced `$script:TrustedProgramData` via `[Environment]::GetFolderPath([Environment+SpecialFolder]::CommonApplicationData)` (native shell API). All `$env:ProgramData` references replaced.

**`SystemRoot` registry resolution failure (HIGH):** The v0.78 fix used `[Environment]::GetEnvironmentVariable('SystemRoot', 'Machine')`, but `SystemRoot` is a kernel-injected variable not reliably present in `HKLM\...\Session Manager\Environment` across all configurations. The call returns `$null`, silently falling back to `C:\Windows`. Systems with the OS installed on another drive (e.g., `D:\Windows`) would fail to find any binaries. **Fix:** Replaced with `[Environment]::GetFolderPath([Environment+SpecialFolder]::Windows)` which calls the native Win32 shell API and resolves correctly regardless of installation drive.

**Browser launch via `ShellExecute` from elevated context — LPE to admin (HIGH):** `Start-Process` on an `http://` URL uses `ShellExecute`, which queries `HKCU\Software\Classes` for the protocol handler. A standard user can register an attacker-controlled executable as the `http` handler. Because the parent PowerShell process is elevated, `ShellExecute` launches the attacker's executable as Administrator. **Fix:** Browser launch routes through `explorer.exe`, which always runs at medium integrity (non-elevated). The browser process it spawns inherits the non-elevated token, so even a poisoned protocol handler cannot obtain admin privileges. Falls back to printing the URL on failure.

## v0.80 | Bootstrapper Scrub Ordering + AST-Sourced Verified Bytes (104 cumulative findings)

**Bootstrapper error-path auto-loader hijack — LPE to admin (CRITICAL):** The `PSModulePath` and `PATH` scrubs in the bootstrapper were placed on line 12, after the named pipe `Connect()` call and memory stream initialization. If the attacker kills the non-elevated process (destroying the pipe server), the elevated bootstrapper's `Connect(30000)` throws a `TimeoutException`. PowerShell's Extended Type System (ETS) searches for `*.format.ps1xml` data to render the exception, triggering the module auto-loader. Because `PSModulePath` has not been scrubbed yet, the auto-loader reaches into the attacker's poisoned directory and executes the malicious module as Administrator. **Fix:** Environment scrubs moved to the absolute first two lines of the bootstrapper, before any constructor, method call, or pipe connection. The environment is sterile before any operation that could throw an exception.

**Already-elevated execution TOCTOU — LPE to SYSTEM (CRITICAL):** When an administrator runs the script from an already-elevated prompt, the bootstrapper is skipped. The entry point code at the bottom of the script re-read the file from disk via `Resolve-CanonicalScriptPath -Lock` to populate `$script:VerifiedScriptBytes`. PowerShell had already read the file, built the AST, and closed its handle before the script began executing. Between PowerShell's initial parse and the entry point's disk re-read, the attacker swaps the file. The second read captures the attacker's payload with no hash verification. When the admin clicks "Install Monitor," the payload is written to `C:\ProgramData\HardTarget` and registered as a SYSTEM scheduled task. **Fix:** `$script:VerifiedScriptBytes` is now populated from `$MyInvocation.MyCommand.ScriptBlock.ToString()`, which contains the AST that PowerShell actually parsed and is currently executing. The disk file is never re-read. The bytes match what is running, not what is on disk.

**UNC path Substring(7) should be Substring(8) (LOW/BUG):** The string `\\?\UNC\` is 8 characters (indices 0-7). `Substring(7)` preserves the trailing backslash, and prepending `\\` produces `\\\server\share` (three leading slashes). While the Windows object manager typically collapses multiple slashes, the path is technically malformed and could cause resolution failures in stricter environments or specific PowerShell providers. **Fix:** Changed to `Substring(8)`.

## v0.79 | .NET CLR Profiler Hijacking Defense (101 cumulative findings)

**.NET CLR profiler DLL injection — LPE to admin (CRITICAL):** The Common Language Runtime reads `COR_ENABLE_PROFILING`, `COR_PROFILER`, and `COR_PROFILER_PATH` from the process environment during runtime initialization, before any managed code executes. Because `Start-Process -Verb RunAs` inherits the non-elevated process's environment block, a standard user can set these variables to load an arbitrary native DLL into the elevated `powershell.exe` process. The DLL executes as Administrator before the bootstrapper's first line of PowerShell runs. All environment scrubbing inside the elevated process (PSModulePath, PATH) is fundamentally too late for this class of attack because the CLR initializes before PowerShell. The same applies to `CORECLR_*` variables (.NET Core/5+ runtime) and `DOTNET_*` variables (.NET runtime configuration). **Fix (UAC path):** The non-elevated process strips all dangerous CLR/runtime variables (`COR_ENABLE_PROFILING`, `COR_PROFILER`, `COR_PROFILER_PATH`, `CORECLR_ENABLE_PROFILING`, `CORECLR_PROFILER`, `CORECLR_PROFILER_PATH`, `_NT_SYMBOL_PATH`, and all `DOTNET_*` prefixed variables) from its own environment immediately before calling `Start-Process`. The inherited environment block is clean before the elevated process is created. **Fix (already-elevated path):** If `COR_ENABLE_PROFILING=1` or `CORECLR_ENABLE_PROFILING=1` is detected while running elevated, the script aborts immediately. The profiler DLL may already be loaded, but aborting prevents the attacker from leveraging the scanner's elevated dashboard, fix engine, or monitor installation.

## v0.78 | SystemRoot Trust Boundary + Pipe Impersonation Hardening (100 cumulative findings)

**`$env:SystemRoot` poisoning via DLL side-loading — LPE to admin/SYSTEM (CRITICAL):** All security-critical execution paths (`$script:PsExeFull`, `$script:Bin.*`, scheduled task actions in `Install-HardTargetMonitor`) were constructed using `$env:SystemRoot`, which standard users can modify in their own process environment. An attacker sets `SystemRoot=C:\FakeWindows`, copies the real Microsoft-signed `powershell.exe` into the matching directory structure, and plants a side-loadable DLL (e.g., `version.dll`, `netapi32.dll`) next to it. When `Start-Process -Verb RunAs` launches the binary, UAC displays a trusted blue banner (the .exe is genuinely signed), and the DLL loads as Administrator. The same poisoned path propagated into `Install-HardTargetMonitor`, permanently registering the attacker's binary to run as `NT AUTHORITY\SYSTEM` every hour. **Fix:** Introduced `$script:TrustedSystemRoot`, sourced from `[Environment]::GetEnvironmentVariable('SystemRoot', 'Machine')` which reads from the HKLM registry (standard users cannot modify machine-scope environment variables). All execution paths, binary path construction, and scan directory references now use `$script:TrustedSystemRoot` exclusively. Zero remaining references to `$env:SystemRoot` outside of comments.

**Named pipe client impersonation risk (MEDIUM):** The elevated bootstrapper's `NamedPipeClientStream` used a three-parameter constructor that did not explicitly specify `TokenImpersonationLevel`. If an attacker controls the non-elevated process (via same-SID memory injection), the malicious pipe server could attempt `ImpersonateNamedPipeClient` to steal the Administrator token from the connecting elevated client. While modern .NET Framework defaults to `SecurityAnonymous`, older versions have historically been inconsistent. **Fix:** The bootstrapper's pipe client constructor now explicitly passes `[Security.Principal.TokenImpersonationLevel]::Anonymous`, guaranteeing the server cannot request an impersonation token regardless of .NET version.

**Bootstrapper environment scrub ordering (MEDIUM):** The `PSModulePath` and `PATH` scrub in the bootstrapper occurred after the hash verification failure path, which calls `Write-Host` and `Read-Host`. While these specific core cmdlets do not trigger the PowerShell auto-loader, any future modification to the error path (custom formatter, logging function, different cmdlet) would instantly introduce an LPE via module hijacking in the error branch. **Fix:** Environment scrub moved to immediately after `SHA256.Dispose()`, before any conditional logic or cmdlet execution, including the error path.

## v0.77 | UAC Context Bleed: Environment and COM Trust Boundary (97 cumulative findings)

**PSModulePath auto-loader hijacking — LPE to admin (CRITICAL):** UAC elevation via `Start-Process -Verb RunAs` creates a new process with an elevated token, but the process still belongs to the same user profile. It inherits the standard user's `HKCU` registry hive and environment variables. An attacker modifies `HKCU\Environment\PSModulePath` to prepend a directory they control (e.g., `C:\Users\Public\Payload`), drops a malicious PowerShell module there, and waits. When the elevated HardTarget process calls any cmdlet that triggers the PowerShell auto-loader, the auto-loader reads the poisoned `$env:PSModulePath`, discovers the attacker's module first, and implicitly executes it as Administrator. Zero race condition required. The in-memory bootstrapper verifies the script code but not the environment it executes in. **Fix:** `$env:PSModulePath` is replaced with machine-scope only (`[Environment]::GetEnvironmentVariable('PSModulePath', 'Machine')`) in two locations: (1) inside the bootstrapper before `[scriptblock]::Create()`, and (2) at the top of the main script immediately after the elevation check, covering the already-elevated path.

**HKCU COM object hijacking — LPE to admin (HIGH):** `Install-HardTargetMonitor` used `New-Object -ComObject WScript.Shell` to create a Start Menu shortcut. Windows COM resolution checks `HKCU\Software\Classes\CLSID` before `HKLM`. A standard user can create a malicious CLSID entry in their `HKCU` hive pointing to an attacker-controlled DLL or scriptlet. When the elevated process requests the COM object, Windows hands it the attacker's payload. **Fix:** Removed all COM object usage from the codebase. Start Menu shortcut creation eliminated; the scheduled task and Add/Remove Programs registry entry provide sufficient access points for users. Uninstall still cleans up the shortcut file if present from older installations.

**PATH environment variable inheritance — LPE to admin (HIGH):** Same vector class as PSModulePath. A standard user can prepend attacker-controlled directories to `HKCU\Environment\PATH`. After UAC elevation, the merged PATH could resolve attacker binaries before system ones. All native binary calls in HardTarget already use fully qualified `$script:Bin.*` paths (fixed in v0.53), so this is defense-in-depth rather than a direct exploit. **Fix:** `$env:PATH` is replaced with machine-scope only alongside `$env:PSModulePath`, in both the bootstrapper and the main script elevated context.

**Same-SID memory injection — LPE to admin (DOCUMENTED LIMITATION):** A standard user holds `PROCESS_ALL_ACCESS` to any process running under the same SID. An attacker can call `WriteProcessMemory` on the non-elevated HardTarget process, overwriting the in-memory script buffer between the file read and the `ComputeHash()` call. The bootstrapper would then build the hash from the attacker's payload, and the elevated process would verify and execute it. This is a fundamental Windows security boundary: no unprivileged process can defend its own memory space against a same-SID attacker. The only true mitigation is a compiled, signed launcher with Protected Process Light (PPL) or equivalent kernel-enforced isolation, which violates the single-file PowerShell architecture. Documented as a known limitation of the threat model.

## v0.76 | In-Memory Elevation via Bootstrapper + Named Pipe (94 cumulative findings)

**UAC handle-theft TOCTOU via DuplicateHandle — LPE to admin (CRITICAL):** The v0.57-v0.75 elevation mechanism held a `FileStream` lock on the script file while the UAC prompt was displayed. A same-user attacker can use `DuplicateHandle` with `DUPLICATE_CLOSE_SOURCE` to forcefully close the lock handle from the non-elevated PowerShell process. `PROCESS_DUP_HANDLE` access is granted by default between processes running under the same SID. Once the lock is dropped, the attacker overwrites the script file. The `AppInfo` RPC connection (which keeps the UAC prompt alive) remains intact because the parent process was not killed. When the administrator clicks "Yes," the elevated PowerShell process loads and executes the attacker's file, which contains no `-HtHash` parameter, no hash verification, and no integrity check. The entire security model assumed the malicious script would voluntarily validate its own hash. It will not. **Fix:** The elevated process never reads from disk. The non-elevated process reads the script into memory via the locked `FileStream` (microsecond hold), releases the lock, creates an admin-only `NamedPipeServerStream` (Administrators ACL, `maxNumberOfServerInstances=1`), generates a tiny bootstrapper script with the pipe name and expected SHA256 hash hardcoded as string literals, Base64-encodes it, and launches the elevated process via `Start-Process -Verb RunAs -ArgumentList "-EncodedCommand $base64"`. The encoded bootstrapper is locked into the `AppInfo` RPC call at the moment `Start-Process` is called and is immutable thereafter. After UAC approval, the elevated bootstrapper connects to the named pipe, reads the script content into memory, computes SHA256, compares to the hardcoded hash, and if verified, executes via `[scriptblock]::Create()`. The disk file is irrelevant after the initial read.

**Already-elevated execution path never populated verified bytes — LPE to SYSTEM (HIGH):** When an administrator runs HardTarget from an already-elevated prompt (or via SCCM/Intune deployment), the `$isAdmin` check in STEP B evaluates to true, skipping the bootstrapper entirely. `$script:VerifiedScriptBytes` is never populated. If the script is launched from a user-writable directory, the attacker has an infinite TOCTOU window: the dashboard runs for minutes or hours while the disk file is unlocked and replaceable. When the admin clicks "Install Monitor," `Install-HardTargetMonitor` falls back to `Copy-Item` from the disk path, copying the attacker's payload into the ACL-protected directory and registering it as a SYSTEM scheduled task. **Fix:** The entry point (bottom of script) now resolves, locks, reads into memory, and populates `$script:VerifiedScriptBytes` for all execution paths that reach it without bootstrapper context. `Install-HardTargetMonitor` then writes from memory regardless of how the script was launched.

**Install-HardTargetMonitor copied from disk after in-memory verification (HIGH):** `Install-HardTargetMonitor` used `Copy-Item` to copy the script from `$script:ScriptPath` (a disk path). If the disk file was swapped after the in-memory bootstrapper read it, the install operation would copy the attacker's file into the ACL-protected directory and register it as the trusted monitor baseline. **Fix:** When `$script:VerifiedScriptBytes` is available (bootstrapper-elevated session), `Install-HardTargetMonitor` writes the in-memory verified bytes directly via `[System.IO.File]::WriteAllBytes()`, bypassing the disk file entirely.

## v0.75 | Atomic Resolve-and-Lock + Path Canonicalization Hardening (91 cumulative findings)

**String-based canonicalization TOCTOU — LPE to admin/SYSTEM (CRITICAL):** The v0.74 `Resolve-CanonicalScriptPath` function called `CreateFileW` to open a native handle, resolved the canonical path via `GetFinalPathNameByHandleW`, then *closed the handle* and returned the path as a string. The caller then passed that string to `[System.IO.FileStream]::new($selfPath, ...)`, which opened a *new* handle. In the microsecond gap between `CloseHandle` and `FileStream::new`, an attacker can rename the parent directory (e.g., `Workspace` → `Workspace_Old`) and create a directory junction at the original name pointing to a payload directory. `FileStream::new` natively follows junctions, so it opens, locks, and hashes the attacker's payload file. The non-elevated process passes the payload's hash to the elevated process, which re-resolves through the same junction, matches the payload's hash, and executes it as admin. This completely bypasses the integrity check because the attacker controls both the file content and its hash. **Fix:** New `-Lock` switch on `Resolve-CanonicalScriptPath`. When specified, the function does NOT close the native handle. Instead, it wraps the same `IntPtr` in a `SafeFileHandle` ($ownsHandle=`$true`) and constructs a `FileStream` directly from the `SafeFileHandle`. The function returns a hashtable with both `Path` (the resolved canonical string) and `Stream` (the locked `FileStream`). Resolution and locking are atomic on the *same kernel handle* — there is no gap. The kernel lock on the file prevents renaming its parent directory (`STATUS_SHARING_VIOLATION`), completely neutralizing junction swap attacks. Applied at STEP A (elevated integrity verification) and STEP B (non-elevated launcher). Non-locking callers (entry point, install handlers) continue using the function without `-Lock`, which closes the handle and returns just the path string.

**UNC path truncation to relative path — LPE to admin (CRITICAL):** `GetFinalPathNameByHandleW` returns `\\?\UNC\server\share\path` for network shares. The v0.74 prefix stripping (`Substring(4)`) yields `UNC\server\share\path` — a *relative* path. PowerShell resolves relative paths against the current working directory (e.g., `C:\Users\Admin\Downloads`). An attacker creates the matching directory structure `Downloads\UNC\server\share\` and plants a malicious `HardTarget.ps1`. The elevated process resolves the relative path against CWD, loads the attacker's script, and executes it as admin. The integrity hash check is bypassed because the attacker's script omits it entirely. **Fix:** Explicit UNC prefix detection. If the resolved path starts with `\\?\UNC\`, replace the 7-character prefix with `\\` to produce the correct UNC path `\\server\share\path`. Local drive paths (`\\?\C:\`) continue using `Substring(4)`.

**Volume GUID path truncation to relative path — LPE to admin (CRITICAL):** Same vulnerability class as UNC truncation. On volumes without assigned drive letters (unmounted VHDs, disk partitions without letter assignments), `GetFinalPathNameByHandleW` returns `\\?\Volume{GUID}\path`. The generic `\\?\` prefix strip (`Substring(4)`) yields `Volume{GUID}\path` — a relative path resolvable against CWD. **Fix:** Detect `\\?\Volume{` prefix and keep it intact. The `\\?\Volume{GUID}\path` form is already the canonical absolute path accepted by Windows APIs and .NET `FileStream`.

**Forced degradation to TOCTOU-vulnerable fallback via exclusive file lock — LPE to admin (CRITICAL):** `CreateFileW` returning `INVALID_HANDLE_VALUE` (-1) is a Win32 return value, not a .NET exception. The `catch` block (which guards against `Reflection.Emit` failure) never fires. The `if ($handle -ne ...)` block is skipped entirely. Execution falls through to Attempt 2 — the managed walk-then-open fallback with a TOCTOU gap. An attacker holds an exclusive lock (`FILE_SHARE_NONE`) on the script file, forcing `CreateFileW` to fail with a sharing violation. Once the script degrades to the managed fallback, the attacker releases the lock and wins the race between the `GetAttributes` reparse point check and `FileStream::new`. **Fix:** After the native handle block, if `-Lock` was specified and execution reaches that point (all success paths hit `return` and exit the function early), `exit 1` unconditionally. This prevents any degradation to the managed fallback on security-critical paths.

**Path length buffer overflow forces degradation to TOCTOU-vulnerable mode — LPE to admin (CRITICAL):** The `StringBuilder` capacity and API buffer size were hardcoded to 1024 characters. If the canonical path exceeds 1024 characters (achievable via deep nesting in attacker-controlled directories), `GetFinalPathNameByHandleW` returns the *required* buffer size (e.g., 1050). The `$r -lt 1024` check fails, `$resolved` remains null, and the function silently falls through to the degraded managed heuristic (walk-then-open, with a TOCTOU gap between the reparse point check and `FileStream::new`). **Fix:** Buffer increased to 32,767 characters (`UNICODE_STRING` maximum / Windows extended-length path limit).

**Environmental downgrade via Constrained Language Mode (CLM) — LPE to admin/SYSTEM (CRITICAL):** All v0.74 security primitives (`Reflection.Emit` for P/Invoke, `[Reflection.Assembly]::Load` for `HtNativeFile.dll`) are blocked by Constrained Language Mode. A standard user can set the undocumented `__PSLockdownPolicy=4` environment variable, which is natively inherited by child processes and crosses the UAC boundary when `Start-Process -Verb RunAs` is called. The elevated process inherits CLM, all `try/catch` blocks around native loading fail silently, `$script:HasNativeFileHelper` is set to `$false`, and the script continues with legacy managed APIs — re-enabling every previously patched TOCTOU vulnerability (registry symlink deletion, file symlink races, junction-based path swaps). **Fix:** Two-site fail-closed guard. In `Resolve-CanonicalScriptPath`: if `-Lock` is specified (security-critical context), `Reflection.Emit` failure triggers immediate `exit 1` with diagnostic message identifying CLM as the likely cause. In the `HtNativeFile` assembly loader: if elevated and `[Reflection.Assembly]::Load` fails, immediate `exit 1`. Non-elevated processes continue to degrade gracefully (the installer applies full native protections during `-Install`).

**Asymmetric trust boundary across UAC elevation — LPE to admin (CRITICAL):** The CLM fail-closed guard in `Resolve-CanonicalScriptPath` must apply symmetrically to both the non-elevated launcher and the elevated process. If only the elevated process aborts on native failure, an attacker can induce `Reflection.Emit` failure in the non-elevated process (e.g., via `COR_PROFILER` environment variable loading a profiler DLL that throws on `DefineDynamicAssembly`), exploit the TOCTOU gap in the managed fallback to swap a junction and spoof the hash of a malicious payload. When UAC spawns the elevated process, Windows strips user-level `COR_PROFILER` variables. The elevated process runs without the profiler, `Reflection.Emit` succeeds, and the native API resolves through the attacker's junction, matches the spoofed hash from the degraded non-elevated process, and executes the payload as admin. ## v0.74 | Path Canonicalization + Disk-Free P/Invoke + Registry Fail-Closed (83 cumulative findings)

**UAC elevation TOCTOU via directory junction swap — LPE to admin (CRITICAL):** The v0.57 self-elevation mechanism opens a `FileStream` lock on the script file and passes a pre-computed hash to the elevated process. However, `FileStream` natively follows reparse points: if the script's path traverses a directory junction, the lock targets the *real* file, not the junction. The junction itself is not locked and remains freely swappable. An attacker creates a directory junction pointing to a legitimate directory containing HardTarget, launches the script through the junction, waits for the UAC prompt to appear, deletes the junction (which succeeds because only the *target file* is locked), and creates a normal directory with a malicious `HardTarget.ps1`. When the administrator approves UAC, the elevated PowerShell process resolves the path through the *new* directory and loads the attacker's script, which contains no integrity check — the hash verification is self-referential and only works when the legitimate script is running. The same root cause affects `Install-HardTargetMonitor`: `$script:ScriptPath` retains the junction-based path, so `Copy-Item` copies the malicious file into the ACL-protected directory and `Get-FileHash` registers it as the trusted baseline, achieving persistent SYSTEM-level execution. **Fix:** New `Resolve-CanonicalScriptPath` function resolves the script's own path through all reparse points before any security operations. Primary method: `Reflection.Emit` dynamic assembly defining P/Invoke methods for `CreateFileW`, `GetFinalPathNameByHandleW`, and `CloseHandle` — entirely in-memory, no disk I/O, no `csc.exe`, no temp files. This is critical because `Add-Type` (the obvious alternative) writes `.cs` files to the Temp folder before invoking `csc.exe`; when running as SYSTEM, an attacker can oplock the Temp folder, pause the SYSTEM thread during the `.cs` write, inject a malicious C# payload, release the lock, and get their code compiled into SYSTEM context. `Reflection.Emit` bypasses the filesystem entirely. Fallback (constrained environment): walks each directory component checking `GetAttributes` for `ReparsePoint` flag and aborts with `SECURITY ABORT` if any component is a reparse point. Applied at STEP A (elevated integrity verification), STEP B (non-elevated launcher hash computation and `Start-Process` invocation), script entry point (`$script:ScriptPath`), and all `Install-HardTargetMonitor` call sites (CLI `-Install`, interactive menu, dashboard server endpoint).

**Auth token leaked via URL fragment in browser launch process (MEDIUM):** The v0.71 auto-auth mechanism passed the session auth token as a URL fragment (`#token`) to `Start-Process`, which launches the default browser. While fragments are never sent in HTTP requests (invisible to servers, proxies, and Referer headers), `Start-Process` passes the full URL including the fragment as a command-line argument to the browser executable. Any standard user can query `Win32_Process` via WMI to read the `CommandLine` property of all running processes, capturing the token. The auth token is a credential — its exposure allows authentication to the localhost server to extract security posture data or trigger shutdown. **Fix:** Token removed from the URL entirely. Browser opened to the bare server URL. Dashboard shows the manual authentication prompt where the operator pastes the token from the PowerShell console. Token also written to the ACL-protected `auth_token.txt` file for programmatic access. The pre-elevation hash (`-HtHash`) and mode (`-HtMode`) remain on the elevated process command line by design: the hash is a public integrity check (not a secret — knowing it provides no attack advantage without SHA256 preimage resistance), and command-line arguments are *immutable* after `Start-Process` is called — the Windows kernel captures them before the UAC prompt. This immutability is the critical security property: even if an attacker kills the parent process (dropping the `FileStream` lock) and swaps the script file, the elevated process still reads the ORIGINAL hash from its own command line and detects the mismatch. Named pipe IPC was evaluated as an alternative but rejected: killing the parent destroys the pipe, allowing the attacker to create a spoofed pipe with the same name and feed a fake hash matching the swapped malicious file.

**SafeRegistryDeleteTree forced degradation to TOCTOU-vulnerable mode (MEDIUM):** When the native P/Invoke DLL is loaded and `SafeRegistryDeleteTree` returns `-1` (error), `Remove-RegistryKeySafe` fell back to the v0.53 degraded managed mode: `Test-RegistrySymlink` (check) followed by `Remove-Item` (act), with a documented TOCTOU window between the two. An attacker can intentionally cause the native operation to fail — by creating deeply nested subkeys exceeding native path length limits, holding oplocks on specific subkeys, or triggering resource exhaustion — forcing the elevated SYSTEM process into the vulnerable fallback path. Once in degraded mode, the attacker executes the registry symlink swap race to delete arbitrary hives (`HKLM\SYSTEM`, `HKLM\SAM`). **Fix:** Two-tier fail-closed behavior. In interactive mode (admin at console): when the native DLL is loaded and `SafeRegistryDeleteTree` returns an error, the function refuses to delete the key, logs a security warning, and returns `$false`. The key is left in place and may require manual cleanup. In Monitor mode (SYSTEM scheduled task, headless): `[Environment]::FailFast()` terminates the process immediately with no cleanup, writes to Windows Error Reporting for forensic trail. A native security operation failure in a headless SYSTEM context is a strong signal of active tampering — the environment is potentially compromised and no further execution should occur. Degraded managed mode is now only reachable when the native DLL was never loaded (PS 5.1 type resolution failure, missing DLL file), not as a fallback from a native operation failure.

## v0.70 | Write-SafeFile Native Opens + Staging Directory Pattern + Registry P/Invoke (73 cumulative findings)

**Write-SafeFile handle check was ineffective — symlink-following file corruption as SYSTEM (CRITICAL):** The v0.67 fix replaced path-based `GetAttributes` with handle-based `IsHandleReparsePoint` to detect symlinks during file writes. However, .NET's `FileStream` constructor follows symlinks transparently before opening — the returned `SafeFileHandle` belongs to the **target** file (e.g. `hal.dll`), not the symlink. Calling `IsHandleReparsePoint` on the target handle always returns false because the target is a normal file. An attacker in an ACL-compromised directory plants a symlink at the drift log path pointing to a system binary; the SYSTEM monitor calls `FileStream::new`, the kernel follows the link, opens `hal.dll`, the handle check passes, and JSON data is appended to the binary. **Fix:** New `HtNativeFile.SafeOpenForAppend(path)` and `HtNativeFile.SafeCreateNew(path)` P/Invoke methods use native `CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT`, which instructs the kernel to open the **link itself** rather than following it. The handle is then checked for the reparse point attribute — if the path was a symlink, the handle points to the symlink object and the attribute is set. Hardlinks are rejected via `nNumberOfLinks > 1`. The verified `SafeFileHandle` is wrapped in a .NET `FileStream` for managed write access. `Write-SafeFile` now uses these native methods for all file operations when P/Invoke is available. Degraded mode retains managed `FileStream` with path-based checks — ACL-protected parent directories remain the primary defense in that mode. DLL recompiled from 5632 → 8192 bytes with all new methods.

**Init block and installer directory security TOCTOU — Set-Acl applied to junction target (MEDIUM):** The v0.69 init block fix and the v0.55 installer both used a check-then-act pattern: detect hostile directory → move aside → create fresh → apply ACLs. Between `Move-Item` (removing the hostile directory) and `Set-Acl` (locking down the new one), an attacker can recreate the directory and swap it for a junction. `Set-Acl` follows the junction and applies the restrictive ACL to the target (e.g. `C:\Windows\System32`), stripping inherited permissions and bricking the OS. **Fix:** New `Initialize-SecureDirectory` helper implements the **staging directory pattern**. It creates a directory with a randomized name (unpredictable to attackers), applies the full ACL lockdown (owner verification, inheritance disabled, SYSTEM+Administrators only), then atomically renames it to the final path via `HtNativeFile.SafeRenameDirectory`. The attacker cannot race because they don't know the staging name, and the ACLs are applied before the directory appears at the known path. Post-rename verification confirms the directory is not a reparse point and has correct ownership. Both the global init block and `Install-HardTargetMonitor` now call this single hardened helper, eliminating duplicated security logic. Degraded mode (no P/Invoke) uses direct create + ACL with documented TOCTOU window.

**Remove-RegistryKeySafe TOCTOU — arbitrary registry hive deletion (CRITICAL):** `Test-RegistrySymlink` closes its .NET `RegistryKey` handle after comparing the resolved path against the expected path. Between handle close and `Remove-Item` execution, a standard user can swap their `HKEY_USERS\{SID}\...\BagMRU` key for a `REG_LINK` pointing to `HKLM\SYSTEM`. PowerShell's `Remove-Item` follows the link transparently and deletes the entire system hive as SYSTEM, bricking the OS. This was documented since the v0.56 changelog as a "known limitation requiring P/Invoke to NtOpenFile with FILE_OPEN_REPARSE_POINT" but the registry equivalent was never implemented despite the filesystem version being fixed in v0.68. **Fix:** New `HtNativeFile.SafeRegistryDeleteTree(hiveName, subKeyPath)` P/Invoke method opens every key with `REG_OPTION_OPEN_LINK` via `RegOpenKeyExW` (prevents the kernel from following registry symlinks), checks for `SymbolicLinkValue` of type `REG_LINK` to detect symlinks, recursively enumerates and deletes all children through handles, and calls `NtDeleteKey` (handle-based, atomic) on each key. No TOCTOU window exists because the handle used for symlink verification is the same handle used for deletion — there is no close-then-reopen gap for an attacker to exploit. `Remove-RegistryKeySafe` now calls this native method when P/Invoke is available. Degraded mode retains the v0.53 check-then-act pattern with its documented TOCTOU window.

**Initialize-SecureDirectory trusted-owner fast path TOCTOU — Set-Acl applied to junction target (MEDIUM):** The v0.70 staging directory pattern correctly eliminated the race for new directory creation, but included a fast-path optimization for existing directories with trusted owners that bypassed the staging pattern entirely. For untrusted owners, the lock is released before `Move-Item` (which requires DELETE access). Degraded mode retains path-based checks with documented TOCTOU window.

If an attacker holds an opportunistic lock (oplock) on the target directory path, the staging directory rename fails, the exception is caught, and the script proceeds using the attacker-owned `C:\ProgramData\HardTarget`. When the admin subsequently installs the monitor, the scheduled task executes attacker-controlled content as SYSTEM. Degraded mode uses `Test-ReparsePoint` check before enumeration with documented TOCTOU window.

## v0.67 | Write-SafeFile Handle Check + JSON Regex DoS + Remediation Gaps (62 cumulative findings)

**Write-SafeFile append-mode TOCTOU — arbitrary file corruption (CRITICAL):** The append-mode reparse point check used `[System.IO.File]::GetAttributes($Path)` to verify the file wasn't a symlink while holding the `FileShare.None` lock. This is fundamentally flawed: `FileShare.None` locks the *target* of a symlink, not the symlink itself. An attacker creates a symlink at `HardTarget_drift.ndjson` → `C:\Windows\System32\hal.dll`. The SYSTEM monitor opens the FileStream (which follows the symlink and locks `hal.dll`). The attacker deletes the symlink and replaces it with a normal text file. `GetAttributes($Path)` queries the path string, sees the new normal file, passes the check. The FileStream appends JSON drift data to `hal.dll`, corrupting the system binary. **Fix:** New `HtNativeFile.IsHandleReparsePoint(SafeFileHandle)` method added to the precompiled P/Invoke DLL. Queries the kernel file object via `GetFileInformationByHandle` on the open `SafeFileHandle` — checks the actual file descriptor, not the path. Cannot be fooled by swapping the path target between open and check. Also applied to create-mode post-create verification. Degraded mode (no P/Invoke) falls back to the path-based check as best effort. DLL recompiled and re-embedded.

**Persistent scanner DoS via JSON truncation regex (MEDIUM):** The post-serialization depth check `$jsonOutput -match 'System\.Collections\.(Hashtable|OrderedDictionary|ArrayList)'` evaluated the entire raw JSON payload with an unanchored regex. A standard user can intentionally crash the scanner by creating a folder named `System.Collections.Hashtable` (captured in ShellBags) or setting a Wi-Fi network SSID to that exact string (logged in Network Profiles). The scanner captures the string, the regex matches it, and throws a hard error — permanently blinding the scheduled monitor task on every subsequent run. **Fix:** Regex now matches only the exact format PowerShell produces when truncating: the type name as a standalone JSON string value preceded by `:` or `[` and followed by `,` `}` or `]`. User-controlled strings containing the type name within larger contexts (folder names, SSIDs, descriptions) will not match the anchored pattern.

**Incomplete remediation for fs-recent-docs and fs-jump-lists (LOW):** The `fs-recent-docs` and `fs-jump-lists` fixes set registry policies (`NoRecentDocsHistory`, `NoRecentDocsMenu`) to halt future tracking, but did not delete existing `.lnk` files from `%APPDATA%\Microsoft\Windows\Recent` or `.automaticDestinations-ms` / `.customDestinations-ms` files from the `AutomaticDestinations` and `CustomDestinations` folders. Because the scanner counts these files, applying the fix left the existing forensic data exposed and the scanner permanently reported "Failed" even after fix application. **Fix:** Post-registry cleanup now iterates `C:\Users\*` to delete all historical Recent Documents `.lnk` files and Jump List destination files across all user profiles.

## v0.63 | Add-Type Oplock Hijacking Fix (55 cumulative findings)

**Add-Type oplock hijacking — SYSTEM privilege escalation (CRITICAL):** When `Add-Type` compiles C# P/Invoke code, PowerShell writes temporary `.cs` and `.cmdline` files to `$env:TEMP` and invokes `csc.exe` to compile them. Restored immediately in a `finally` block. Standard users cannot read or write to this directory, eliminating the oplock attack surface. Long-term fix: precompile the DLL, base64-encode it, and load via `[Reflection.Assembly]::Load($bytes)` — zero disk I/O, zero `csc.exe` invocation.

## v0.62 | ACL Preservation LPE Fix (54 cumulative findings)

**ACL Preservation local privilege escalation (CRITICAL):** Full SYSTEM code execution via file ACL persistence. The global initialization unconditionally created `C:\ProgramData\HardTarget` without custom ACLs — the directory inherited permissions from `C:\ProgramData`, granting `BUILTIN\Users` WriteData/AddFile. ## v0.58 | P/Invoke Atomic File Deletion + Regression Fixes (45 cumulative findings)

**Atomic link-safe file deletion via P/Invoke (CRITICAL):** Managed .NET APIs (`File.Delete`, `Remove-Item`) cannot atomically verify link status before deletion. `File.Delete` on a symlink removes the symlink (safe), and on a hardlink removes one directory entry (safe), but the check-then-delete pattern still has a TOCTOU window where an attacker can swap a normal file for a link. **Fix:** Added `HtNativeFile.SafeDeleteFile()` via Add-Type P/Invoke. ## v0.57 | Architectural Rewrite: Eliminate BAT as Security Boundary (41 cumulative findings)

**Architectural rewrite: eliminate BAT as security boundary (CRITICAL):** Versions 0.52-0.56 attempted to secure the UAC elevation boundary using `RUN_HardTarget.bat`. Each fix introduced new attack surface because `cmd.exe` fundamentally lacks atomic file operations, secure I/O, and reliable concurrency primitives. The v0.56 temp file fix broke already-elevated administrators; the certutil direct-parse fix had nested quoting failures; the staging directory approach was vulnerable to junction attacks. **Fix:** Deleted all security logic from the BAT (now a 5-line launcher). Moved menu, elevation, hashing, and integrity verification entirely into `HardTarget.ps1`. The new flow: non-elevated PS1 opens itself with `FileStream(FileAccess.Read, FileShare.Read)` -- a kernel-level lock that physically prevents any process from writing or deleting the file. It computes SHA256 from the locked stream, launches the elevated copy via `Start-Process -Verb RunAs`, and **holds the lock during the entire UAC prompt** by calling `WaitForExit()`. The elevated PS1 opens the same file (read sharing is compatible), reads all bytes, hashes them, and compares to the baseline argument. If match, execution continues. If mismatch, hard abort. No temp files. No staging directories. No `certutil`. No `%RANDOM%`. The TOCTOU window is closed at the kernel level.

**Arbitrary file overwrite in fs-ps-history (CRITICAL):** Every attempt to safely overwrite user-controlled files (v0.53-v0.56) had an inherent TOCTOU. The check-then-write pattern cannot be made atomic in PowerShell for files where standard users control the parent directory. An attacker can always swap the file for a hardlink to SAM/LSA between the check and the write, causing the elevated process to corrupt the OS. **Fix:** Eliminated in-place overwrite entirely. `fs-ps-history` now uses `[System.IO.File]::Delete()` only. `Delete` on a hardlink removes just the directory entry without affecting the linked target. `Delete` on a symlink removes the symlink, not the target. Both are inherently safe. The anti-forensic random-byte overwrite is sacrificed -- privacy benefit does not justify OS destruction risk.

**Data destruction in Write-SafeFile append mode (HIGH):** The v0.56 fix changed append mode to delete-then-CreateNew with only new content, destroying the entire historical `HardTarget_drift.ndjson` log every hour. **Fix:** Restored in-place append for ACL-protected paths. The drift log lives in `C:\ProgramData\HardTarget`, which is locked to Administrators+SYSTEM only -- standard users cannot create hardlinks or symlinks there. Append mode now opens with `FileShare.None` (exclusive lock), re-verifies the file is not a reparse point while holding the lock, then appends through the locked handle. Delete-then-CreateNew is used only for create/overwrite operations.

## v0.56 | Fix Regressions from v0.55 + Red Team Findings (38 cumulative findings)

**Arbitrary file read (SAM/LSA dump) via Write-SafeFile append (CRITICAL):** The v0.55 "read-delete-CreateNew" pattern for append mode called `ReadAllText` after a hardlink check but before acquiring a file lock. An attacker could swap the target for a hardlink to `SAM` or `LSA` between the check and the read, causing the elevated SYSTEM process to read the hive contents and write them into an attacker-controlled file. **Fix:** Append mode no longer reads existing content. All writes use unconditional delete-then-CreateNew with only the new content. No read = no exfiltration vector.

**Temp file hijacking in BAT staging (CRITICAL):** The certutil temp file approach used `%RANDOM%` (0-32767) for filenames in user-writable `%TEMP%`. The certutil redirect fails silently, and `for /f` reads the attacker's hash. **Fix:** Eliminated temp files entirely. certutil output is parsed directly in `for /f` -- the certutil.exe path has no spaces, so no quoting collision occurs inside the single-quoted command string.

**Dead hardlink check in fs-ps-history (HIGH):** The v0.55 fix opened the history file with `FileShare.None`, then attempted `Get-Item` to check hardlinks. Because the script holds an exclusive lock, `Get-Item` triggers a sharing violation. LinkType`) before the `FileStream` open. Removed the dead code from inside the lock. **Arbitrary ACL override via monitor install junction race (HIGH):** If `C:\ProgramData\HardTarget` does not exist, the entire validation block is skipped. Post-check detects if an attacker won the race and throws a hard abort.

**Write-SafeFile CreateNew symlink race (HIGH):** An attacker plants a symlink between `Delete` and `CreateNew` pointing to a non-existent file in a privileged directory. `CreateNew` follows the symlink and creates the target. **Fix:** After `CreateNew`, while holding the `FileStream`, verify the path isn't a reparse point via `GetAttributes`. **AllUsers flag regex failure on PS 5.1 (MEDIUM):** The `-match '^HKCU:\\'` regex may fail silently on PowerShell 5.1 due to backslash escaping differences. **Fix:** Replaced with `-like 'HKCU:\*'` (wildcard, no regex) and `.Substring(6)` for prefix stripping.

**Remove-ItemSafeRecurse inherent TOCTOU (MEDIUM, documented):** The check-then-delete pattern has an inherent race condition that cannot be fixed in pure PowerShell/.NET. Updated documentation to explicitly state the limitation and the P/Invoke approach required for a complete fix.

**Predictable temp file symlink (HIGH):** `Get-SecurityPolicy` creates temp file using `Get-Random` which in PowerShell 5.1 is seeded by `Environment.TickCount` (predictable by local attacker). When monitor runs as SYSTEM, `$env:TEMP` resolves to `C:\Windows\Temp` (user-writable). Attacker predicts filename, pre-creates it as symlink. `secedit.exe` follows link, overwrites target file with policy data. **Fix:** Filename now uses CSPRNG (`RandomNumberGenerator`), 32 hex chars. **Unqualified binary paths in BAT launcher (CRITICAL):** `RUN_HardTarget.bat` invokes `powershell`, `cmd.exe`, `net`, and `icacls` using bare names. **Blind admin lockout via Disable-LocalUser (HIGH):** Script disables the built-in Administrator (`SID *-500`) without verifying that another active admin account exists. On machines where *-500 is the only admin (kiosks, legacy deployments, lab environments), this permanently locks out all administrative access, requiring offline SAM registry edits via boot USB to recover. **Fix:** Before disabling, enumerates the Administrators group via `Get-LocalGroupMember -SID 'S-1-5-32-544'` (locale-independent). **False-positive firmware-forced S0 detection (HIGH):** When `PlatformAoAcOverride=0` was set and `powercfg /a` still listed S0 with no S3 fallback, the logic assumed the override was ineffective and reported "FIRMWARE-FORCED" as a fail. With no S3 either, the machine has no sleep state — lid close triggers shutdown. That's the best possible security outcome, not a failure. **Fix:** Override-set + no-S3 now correctly reports as pass ("All sleep states disabled"). True firmware-forced status only fires when S0 is active and the override has NOT been applied, informing the user that applying it will disable all sleep (lid close = shutdown) since there's no S3 to fall back to. Status changed from `fail` to `warn` with clear messaging about the tradeoff.

**Staging directory LPE introduced by v0.52 TOCTOU fix (CRITICAL):** The secure staging routine copied the payload to `%SystemRoot%\Temp\HardTarget` — a predictable name in a standard-user-writable directory. An attacker pre-creates the directory, becomes CREATOR OWNER, retains implicit WRITE_DAC regardless of `icacls` DACL restrictions, can restore full access and swap the payload between hash verification and execution. **Fix:** Staging directory now uses a CSPRNG random name (`HT_{16 hex chars}`) generated via `RandomNumberGenerator`. If the directory already exists (astronomically unlikely), aborts rather than reusing it. Also adds `/setowner "BUILTIN\Administrators"` to the `icacls` command as defense-in-depth. Directory and contents cleaned up after execution via `:StageCleanup`.

**Write-SafeFile dead code — all file writes still vulnerable (HIGH):** The `Write-SafeFile` helper was defined but never called. All 18 `Out-File` calls in the monitor, scan output, install, and web server code paths continued to use raw `Out-File`, leaving the arbitrary file overwrite via symlink vulnerability completely unmitigated. **Fix:** All `Out-File` calls outside of `Write-SafeFile` itself and the verify wrapper (which runs in a separately secured context) are now routed through `Write-SafeFile`. This includes integrity logs, baseline files, golden baseline, drift logs, scan JSON, alert files, and error logs.

**BitLocker PIN plaintext in managed heap (MEDIUM):** The v0.52 fix correctly used `SecureStringToBSTR` and `ZeroFreeBSTR`, but extracted the BSTR into a standard PowerShell string via `PtrToStringBSTR` for length and equality checks. .NET strings are immutable — setting `$pinPlain = $null` removes the reference but the actual string data persists in the managed heap until GC collection and memory reuse, completely defeating the BSTR zeroing. **Fix:** Length validation now uses `$securePin.Length` directly (SecureString exposes `.Length`). Equality comparison uses `Marshal.ReadInt16` pointer arithmetic on BSTR pointers, comparing character-by-character without ever creating managed string objects. Comparison is constant-time (no early break on mismatch).

**Install-HardTargetMonitor ACL junction attack (HIGH):** `Install-HardTargetMonitor` applied ownership and DACL operations to `$monDir` without checking if it was a reparse point. A standard user can pre-create `C:\ProgramData\HardTarget` as a junction pointing to `C:\Windows\System32`. `Get-Acl`/`Set-Acl` follows the junction transparently, stripping permissions from System32 and breaking the OS. **Fix:** `Test-ReparsePoint` check added at the very beginning of the install routine. If a junction/symlink is detected, the link is deleted before any ACL or ownership operations proceed. Failure to remove aborts with `SECURITY ABORT`.

**Verify wrapper TOCTOU race (HIGH):** `HardTarget_Verify.ps1` computed the SHA256 hash of the monitor script on disk, then passed the file path to a new `powershell.exe` process via `-File`. An attacker with write access can swap the file contents between the hash check and the new process reading the file. **Fix:** Wrapper now uses `[System.IO.File]::ReadAllBytes()` to read the entire script into memory, computes SHA256 from the in-memory bytes, and executes the verified content via `[scriptblock]::Create()`. No file path is passed to a new process — execution happens from the same verified byte array.

**Unqualified system binaries in PowerShell (HIGH):** While the BAT launcher was fixed, `HardTarget.ps1` itself invoked `manage-bde`, `powercfg`, `bcdedit`, `secedit`, `vssadmin`, and other system utilities using bare names. Standard users can modify their User `PATH`, and UAC elevation merges User PATH into System PATH, allowing an attacker to redirect these commands to malicious executables. **Fix:** `$script:Bin` hashtable defined at script initialization with fully qualified `$env:SystemRoot\System32\...` paths for all system binaries. All 16 runtime invocations and 6 Command strings in fix definitions updated. Command whitelist validation updated to match against qualified paths.

**Broken UAC TOCTOU mitigation in BAT staging (CRITICAL):** The secure staging subroutine computed the hash of the source file *after* UAC elevation. If an attacker swapped the PS1 during the UAC prompt, the elevated process simply copied the malicious file, hashed the malicious source, confirmed it matched the malicious copy, and executed. **Fix:** Hash is now computed *before* the UAC prompt via `:PreElevateHash` subroutine and passed to the elevated process as a command-line argument. The elevated `:SecureStage` verifies the staged copy against this pre-elevation baseline — not against the current source file. If no baseline is available (already-elevated user), falls back to source-vs-copy verification since no UAC window was shown.

**TOCTOU in Remove-ItemSafeRecurse (MEDIUM):** The check-then-delete pattern (`Test-ReparsePoint` followed by `Remove-Item`) has a race window where an attacker can plant a junction after the check passes. **Fix:** Re-reads attributes via `[System.IO.File]::GetAttributes()` immediately before each delete operation and before removing the root directory, narrowing the window to microseconds. Acknowledges that a truly atomic solution requires P/Invoke with `FILE_FLAG_OPEN_REPARSE_POINT` handles, which is beyond pure PowerShell.

**TOCTOU in Write-SafeFile (MEDIUM):** Same check-then-write race: an attacker swaps the target for a symlink between the reparse check and `Out-File`. **Fix:** Replaced `Out-File` with `[System.IO.FileStream]`. New files use `FileMode.CreateNew` for atomic creation (fails if anything exists). Append operations open with `FileShare.None` (exclusive lock) and re-verify attributes while holding the lock. Overwrites delete-then-CreateNew to prevent following attacker-planted links. Acknowledges remaining theoretical window requiring P/Invoke for full closure.

**Registry symlink arbitrary deletion (CRITICAL):** The `fs-user-assist` and `fs-shellbags` fix blocks enumerate `HKEY_USERS\{SID}\...` and call `Remove-Item -Recurse`. Standard users have full control over their own hive and can plant registry symbolic links (via `NtCreateKey` with `REG_OPTION_CREATE_LINK`) pointing to `HKLM\SYSTEM`, `HKLM\SAM`, or other critical hives. PowerShell's `Remove-Item` follows registry symlinks natively, causing the elevated SYSTEM process to permanently delete critical OS hives. **Fix:** Three new helper functions: `Test-RegistrySymlink` opens keys via `[Microsoft.Win32.RegistryKey]` and compares the resolved `Name` against the expected path (REG_LINK keys resolve to their target); `Remove-RegistryKeySafe` wraps deletion with symlink detection for the key and all children; both `fs-user-assist` and `fs-shellbags` now use `Remove-RegistryKeySafe` for all user-hive operations.

**Unqualified powershell.exe in elevated contexts (HIGH):** Despite fixing bare binary names in the BAT launcher and PS1 runtime calls, three persistent references remained: the scheduled task (`New-ScheduledTaskAction -Execute 'powershell.exe'`), the Start Menu shortcut (`TargetPath = 'powershell.exe'`), and the Add/Remove Programs uninstall command. All run as SYSTEM or in elevated contexts, vulnerable to PATH hijacking. **Fix:** All three now use `$psExeFull = Join-Path $env:SystemRoot 'System32\WindowsPowerShell\v1.0\powershell.exe'`.

**Session 0 UI deadlock in monitor (MEDIUM):** When drift was detected, the monitor attempted to show a `System.Windows.Forms.NotifyIcon` balloon tip, then called `Start-Sleep -Seconds 16` before disposing it. Since the scheduled task runs as SYSTEM in Session 0, Session 0 isolation (enforced since Vista) prevents any UI elements from rendering on the interactive user's desktop. The balloon silently failed to appear, and the 16-second sleep needlessly blocked the monitor on every drift detection. **Fix:** Removed the `NotifyIcon`/`BalloonTip` block entirely. User-visible alerting is handled by `msg.exe` (which can target interactive sessions) and the human-readable alert file. SIEM ingestion uses Event Log entries.

**Privilege escalation via path injection in BAT staging (CRITICAL):** The `PreElevateHash` and `SecureStage` subroutines passed file paths unescaped into `powershell.exe -Command` strings using single-quote delimiters. A standard user who places the script inside a directory with a crafted name containing PowerShell syntax (e.g., `C:\Temp\A'; Invoke-Payload; '#\`) can inject arbitrary commands that execute in the elevated High-IL PowerShell context when an administrator approves the UAC prompt. **Fix:** Replaced all PowerShell-based hashing with `certutil -hashfile`, a native Windows binary that treats the path as a literal filename with no interpretation or injection surface. Also switched `%~sdp0` (short name, breaks when 8.3 disabled) to `%~dp0` (long path).

**LPE via localized BUILTIN\Administrators in ACL application (CRITICAL):** `Install-HardTargetMonitor` hardcoded the English string `'BUILTIN\Administrators'` and `'NT AUTHORITY\SYSTEM'` when constructing `NTAccount` objects and `FileSystemAccessRule` entries. On non-English Windows, these strings cannot be translated to SIDs and the constructor throws. The `try/catch` logged a warning but continued installation, leaving the monitor directory writable by standard users with default `ProgramData` permissions. **Fix:** All ACL operations now use well-known SIDs (`S-1-5-32-544` for Administrators, `S-1-5-18` for SYSTEM) translated via `SecurityIdentifier.Translate()`. The catch block is now a hard abort -- installation does not continue with an insecure directory. BAT staging `icacls` also switched to SID syntax (`*S-1-5-32-544`).

**Installer ACL junction attack / TOCTOU race (HIGH):** Despite the `Test-ReparsePoint` check, the install routine remained vulnerable to a race condition. A standard user pre-creates the directory (becoming CREATOR OWNER with Delete rights), the script sees an untrusted owner and prepares to apply ACLs, but the attacker uses their Delete right to remove the directory and plant a junction to System32 before `Set-Acl` executes. **Fix:** If the directory exists with an untrusted owner (checked via SID), it is treated as hostile and moved aside atomically via `Move-Item` to a random name. The script then creates a fresh directory as SYSTEM, ensuring standard users lack the Delete right needed to race. ACLs are only applied to directories created by the elevated process.

**Arbitrary file overwrite TOCTOU in fs-ps-history (HIGH):** The `fs-ps-history` fix used `Test-ReparsePoint` followed by `[System.IO.File]::WriteAllBytes()`, which follows symlinks and hardlinks. A standard user can swap their `ConsoleHost_history.txt` for a link to a critical system file in the window between the check and the write. **Fix:** Replaced with `FileStream`-based approach: open with exclusive lock (`FileShare.None`), re-verify attributes and hardlink status while holding the lock, then overwrite and truncate through the locked handle. No `WriteAllBytes` or `Set-Content` calls.

**Hardlink TOCTOU in Write-SafeFile append mode (MEDIUM):** In append mode, `Write-SafeFile` opened the existing file with an exclusive `FileStream` lock and re-verified reparse point attributes. However, `GetAttributes` does not detect hardlinks (they are not reparse points). An attacker could swap the target for a hardlink between the pre-lock check and the lock acquisition. **Fix:** Append mode no longer opens existing files for in-place modification. Instead, it reads existing content, deletes the file, and uses `FileMode.CreateNew` to write old+new content atomically. All write paths now use the delete-then-CreateNew pattern.

**Incomplete UAC context mismatch fixes (MEDIUM):** While `fs-user-assist`, `fs-ps-history`, and `fs-shellbags` were updated to iterate `HKEY_USERS`, three forensic registry fixes (`fs-recent-docs`, `fs-jump-lists`, `fs-thumbnails`) still exclusively targeted `HKCU:\`. When run via UAC elevation, these only modified the admin account's hive. **Fix:** Added `AllUsers = $true` flag to these fix definitions. The registry fix handler now iterates all loaded user hives in `HKEY_USERS` (matching `S-1-5-21-*` SIDs) in addition to `HKCU` when this flag is set.

## v0.43 | Access control chain, AMT awareness, stable filenames

**NEW CHECK: UAC credential prompt behaviour (MEDIUM):** Reads `ConsentPromptBehaviorAdmin` from the System policy registry key. Distinguishes between silent elevation (fail, value 0), consent-only prompt (warn, value 5/default), and credential prompt (pass, value 1 or 3). The default Windows setting shows a simple Yes/No dialog - an attacker at an unlocked admin session clicks Yes and gets full administrator privileges. Fix available: sets `ConsentPromptBehaviorAdmin=1` to require password re-entry on every elevation. Mapped to evil-maid and coercion scenarios.

**NEW CHECK: Local admin account password presence (MEDIUM):** Enumerates all enabled local administrator accounts via `Get-LocalGroupMember` and `Get-LocalUser`. Flags accounts with `PasswordRequired = false` or `PasswordLastSet = null`. Separately checks the built-in Administrator account (SID -500), which bypasses UAC entirely - no consent prompts, no credential prompts, every process runs fully elevated. A passwordless built-in Administrator account means an attacker at the login screen presses Enter and has unrestricted system access. Mapped to evil-maid and coercion scenarios.

**NEW CHECK: Intel AMT provisioning status (LOW):** Informational check in the BIOS/Firmware section. Three detection methods: WMI `root\Intel_ME` namespace query, Intel Local Management Service (LMS) presence, and MEI/HECI PnP driver enumeration. Reports `warn` if AMT appears provisioned, `info` if ME driver is present but provisioning status is unconfirmed. No fix offered (AMT configuration requires BIOS/MEBx access). Security comment documents that AMT does not bypass OS authentication or escalate privileges - it provides remote physical-equivalent access only. Mapped to evil-maid scenario.

**Access control defence chain:** The three new Access Control checks (display timeout, UAC credential prompt, local password) form a coherent defence chain. Display timeout limits the unlocked session window. UAC credential prompt gates what an attacker can do at an unlocked session. Local password ensures the credential gate is real. Each is meaningless without the others. Dashboard info panels explain the chain relationship.

## v0.42 | Security fixes, scenario accuracy, documentation alignment

## v0.39 | Security hardening (red team assessment)

All findings from the v0.38 red team security assessment addressed. No changes to scan logic or fix engine behaviour.

**BAT launcher TOCTOU race condition (HIGH):** Mode selection was written to a temp file before UAC elevation. Any local process could swap the mode between user selection and elevated execution (Audit/Expert). Eliminated temp file entirely; mode now passed as command-line argument to the elevated process.

**Global `$ErrorActionPreference = 'SilentlyContinue'` (HIGH):** All non-terminating errors were silently swallowed script-wide. Security-critical operations (ACL application, registry writes, fix verification) could fail without indication. Changed global to `Stop`; individual cmdlets where failure is expected use explicit `-ErrorAction SilentlyContinue`.

**Localhost HTTP threat model (HIGH):** Documented in code comments and console warning. Operator now informed at startup that plain HTTP means any local process with network visibility can read security posture data. HTTP is a deliberate design choice: all mutations require console confirmation codes that can only be completed with physical access to the PowerShell window, making TLS redundant for integrity. Confidentiality of scan data against local processes is out of scope - an attacker with that access level can run their own scan.

**Origin check bypass (MEDIUM):** Added `Sec-Fetch-Site` header validation as defense-in-depth against browser CSRF. Non-browser tools rely on auth token.

**COMPUTERNAME XSS (MEDIUM):** `$env:COMPUTERNAME` now sanitized via `Sanitize-HtmlString` before inclusion in JSON/dashboard.

**Monitor baseline ratchet (MEDIUM):** Added golden baseline (created on first run, never overwritten) alongside incremental baseline. Cumulative drift now detected even when incremental changes are small.

**Scan JSON output location (MEDIUM):** Default output changed from `%USERPROFILE%\Downloads` to `%ProgramData%\HardTarget`. Console note warns that scan results are sensitive.

**Monitor script integrity check (MEDIUM):** SHA256 hash verified against `InstalledHash` registry value before each monitor run. Mismatch logs critical event (EventId 9999) and aborts.

**JSON depth truncation detection (MEDIUM):** Post-serialization check for `System.Collections.Hashtable` truncation markers.

**Port-squatting DoS mitigation (MEDIUM):** New `-Port` parameter for explicit server port override.

**Constant-time auth token comparison (LOW):** All three auth token comparisons now use XOR-accumulation constant-time function.

**CSPRNG confirmation codes (LOW):** `Get-Random` replaced with `RNGCryptoServiceProvider` for all confirmation codes.

**Drift log rotation (LOW):** Rotates at 10MB with one backup.

**Script path validation (LOW):** Fallback to `$MyInvocation.MyCommand.Definition` when `.Path` is `$null`.

**Auth token console warning (LOW):** Console notes that token is visible in scrollback and transcripts.

**Version bump:** 0.38 to 0.39 across all files.
